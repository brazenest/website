# Chat analytics

What the chat home reports to PostHog, and the dashboard to build from it. No visitor text is
stored anywhere: the page sends counts and link facts, and the chat Worker sends labels that a
small model assigns to each exchange, then discards the text.

Reporting only happens where PostHog runs: aldengillespy.com (not localhost, not
dev.aldengillespy.com or *.pages.dev), for visitors who haven't opted out with `?notrack` and
whose browser loads the SDK. Without the visitor's PostHog id the Worker sends nothing.

## Events

All chat events share `answer_id` (generated by the Worker for each answer) and `turn` (which
question of the conversation: 1, 2, 3…), so they join on one answer.

| Event | Sent by | Properties |
|---|---|---|
| `chat_question` | page | `turn`, `source` (`typed`, `suggestion`, `rail`) |
| `chat_answered` | page | `answer_id`, `turn`, `source`, `works` (ventures linked), `primary_work` (the one the page re-tinted to), `pages` (hrefs linked), `link_count`, `answer_chars`, `answer_ms` |
| `chat_link_click` | page | `answer_id`, `href`, `work`, `kind` (`inline` link or page `chip`) |
| `chat_error` | page | `code` (`rate_limited`, `upstream`, `busy`…), `turn`, `partial` |
| `chat_classified` | Worker | `answer_id`, `turn`, `topics` (1–3), `primary_topic`, `coverage`, `intent`, `refused`, `answer_model`, `first_token_ms`, `answer_ms`, `answer_tokens_*`, `classify_tokens_*` |

Existing site events still apply: `contact_opened`, `contact_submitted`, `resume_downloaded`,
`outbound_click`, plus `$pageview` for the pages the chat links to.

### Labels (`chat_classified`)

- **topics**: a venture slug (`memrey`, `rotavox`, `andacity`, `bolt`, `shadowcat`, generated from
  the Payload ventures), or `career`, `working_together`, `background`, `writing`, `site`,
  `off_topic`, `probing`. `off_topic` and `probing` are always the only topic.
- **coverage**: `answered`, `partial`, `not_covered` (the content doesn't say, or only points to
  /contact), `declined` (off-topic or improper), or `unlabelled` if the labeller failed.
- **intent**: `hiring`, `client`, `collaboration`, `curious`, `probing`, `unclear`.

The labeller is `claude-haiku-5-5` (Worker var `CLASSIFY_MODEL`), about $0.00015 per answer,
run in `ctx.waitUntil` after the answer has streamed. Code: `chat-worker/src/classify.ts`.

## Dashboard: "Chat"

Filter every insight to `primary_topic != probing` unless it's the health panel.

1. **Demand by area**: `chat_classified`, total count, breakdown `primary_topic`, weekly.
2. **Coverage by area**: `chat_classified`, breakdown `primary_topic`, then `coverage`
   (stacked bar). Areas with a high `not_covered` + `partial` share are the content to write next.
3. **Who's asking**: `chat_classified`, breakdown `intent`, weekly.
4. **Answer → click rate by area**: funnel `chat_classified` → `chat_link_click`, within the same
   session, breakdown `primary_topic`. Low rates mean the linked page doesn't pull people in.
5. **Chat → contact**: funnel `chat_question` → `contact_opened` → `contact_submitted`, breakdown
   by the first event's `source`; a second copy starting at `chat_classified` with
   `intent = hiring` or `client`. This is the number the site exists for.
6. **Depth**: `chat_question`, breakdown `turn` (how far conversations go).
7. **Health**: `chat_classified` median `first_token_ms` and `answer_ms`; `chat_error` count by
   `code`; `chat_classified` where `primary_topic = probing` (abuse attempts).
8. **Cost**: sum of `answer_tokens_out`, `answer_tokens_cache_write`, `answer_tokens_in`, weekly
   (Opus 5.5 pricing); the cache-write line spikes when the 1-hour prompt cache goes cold.

Reading it: demand × (1 − coverage) ranks the gaps; for each area, demand, click rate and
contact rate together say whether to write more, improve the linked page, or leave it alone.
